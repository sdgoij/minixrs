# Syncing the Minix Rust fork with upstream

`rust/` is a git submodule pinned to `sdgoij/rust` branch `feature/platform-minixrs`: the
three in-tree Minix target specs plus the whole `std` platform layer
(`library/std/src/sys/pal/minix/`, `sys/pipe/minix.rs`, `sys/net/connection/minix.rs`,
`sys/thread/minix.rs`, `sys/sync/futex/minix.rs`). Rebasing it onto upstream `main` is a
recurring maintenance job, and the version string of the rebuilt compiler changes, which
invalidates every cached artifact in the tree.

Use this skill when syncing the fork, rebuilding the stage1 toolchain, or when a toolchain
change breaks `just bootstrap` / the coreutils build.

## Layout facts

- `rust/config.toml` is generated by `tools/rust-config.py` (which `just bootstrap` runs)
  and lists eight targets: the Windows host, the three Minix triples, their `-elf`
  (position-independent) forms, and `wasm32-minix`. The last four carry `no-std = true` so
  their sysroots hold `core` and `alloc` and no std (`DYNAMIC_LINKING.md` §6.5,
  `ARCH_WASM32.md`). The host must stay listed so `x.py`'s sysroot pruning does not delete its
  std, and a triple must stay listed for its sysroot to exist at all — `Sysroot::run` deletes
  the whole stage1 directory on each bootstrap.
- **A `[llvm]` change does not rebuild LLVM.** `x.py`'s LLVM stamp hashes only the
  `src/llvm-project` checkout (`utils/build_stamp.rs::generate_smart_stamp_hash`), not the
  bootstrap config, so editing `[llvm] targets` — adding `WebAssembly` for `wasm32-minix`, say
  — leaves the old LLVM in place and the backend missing. The symptom is not an LLVM error but
  a `rustc` probe of the new target failing on an unknown `-Cllvm-args`
  (`Unknown command line argument '-wasm-use-legacy-eh=false'`), which reads as a target-spec
  bug. Remove `rust/build/<host>/llvm/.llvm-stamp` — as the stamp's own message says — and
  re-run; the LLVM rebuild is the long part of that bootstrap.
- `[llvm] download-ci-llvm = true`, so builds fetch a prebuilt LLVM. The in-tree
  `rust/src/llvm-project` gitlink is irrelevant to builds — a stale checkout just shows as
  ` M src/llvm-project` and can be ignored (or updated later; the objects are usually local).
- The stage1 toolchain used by every userland/server/smoke build is
  `rust/build/<host>/stage1/bin/rustc[.exe]`; its sysroot is
  `rust/build/<host>/stage1/lib/rustlib/<triple>/lib/`.

## Rebase

```sh
cd rust && git fetch origin
git rebase origin/main
```

Conflicts land in a handful of places:

- `library/std/src/sys/exit.rs`, `library/std/src/sys/personality/mod.rs` — the fork adds a
  `target_os = "minix"` arm; upstream reformats arms and moves OS cases between them (e.g.
  dropping `motor` from the aborting-stub personality arm). Keep upstream's shape and
  re-apply the minix arm in it.
- `src/bootstrap/src/lib.rs` — upstream keeps relocating the file body into
  `src/bootstrap/src/core/`. Take upstream's stub and re-apply the fork's one edit wherever
  it moved (`std_features` now lives in `src/bootstrap/src/core/session.rs`).
- `library/std/src/sys/*/mod.rs` dispatchers — usually conflict-free, but see the API-drift
  audit below; a clean merge can still be wrong.

Prove the resolutions are faithful instead of eyeballing:

```sh
git --no-pager range-diff <old-base>..<pre-rebase-tag> origin/main..HEAD | grep -E '^[0-9]+: '
```

The bar is **every commit `=`** (byte-identical replay); `!` entries are only acceptable when
they differ solely in upstream-refactored surrounding context, and each should be reviewed
line by line. Also confirm no conflict markers survive:

```sh
git --no-pager grep -n -E '^(<<<<<<<|>>>>>>>)' -- library/std compiler/rustc_target src/bootstrap
```

A sync is usually clean *after* the first rebase. Check the conflict surface before rebasing:

```sh
git --no-pager diff --stat <old-base>..origin/main -- library/std/src/sys compiler/rustc_target/src/spec src/bootstrap src/librustdoc
```

Upstream touching none of those paths means a clean replay — a 60-commit sync replayed
8/8 commits as `=` with zero conflicts.

## Build the toolchain — always include proc_macro

```sh
cd rust && python x.py build library/std library/proc_macro
```

**Do not drop `library/proc_macro`.** `x.py build library/std` installs a sysroot containing
std and its dependencies *only*, pruning everything else (no `libproc_macro`, no `test`).
A rebase changes the stage1 compiler's version string (the commit hash is part of it), so
cargo invalidates all fingerprints — including the host proc-macro artifacts under
`coreutils/target/` that normally hide this gap. The first rebuild that needs a host
proc-macro crate then dies with:

```
error[E0463]: can't find crate for `proc_macro`
   --> .../proc-macro2-*/src/lib.rs:...: extern crate proc_macro;
error: recipe `coreutils-x86` failed on line 82 with exit code 101
```

Naming both steps in one invocation makes the sysroot install contain both, so std (host
and all three Minix targets) survives. Confirm with:

```sh
ls rust/build/<host>/stage1/lib/rustlib/x86_64-pc-windows-msvc/lib/ | grep -i proc_macro
```

Related trap: the recipe's root `cargo clean` does **not** clean `coreutils/target/` —
coreutils is in the root workspace's `exclude` list and keeps its own target dir. Left alone, that
dir survives a toolchain rebuild and the multicall then links rlibs built by the *previous* stage1
against the new sysroot. Two symptoms, both measured: the same `E0463` during `just coreutils-x86`
(`can't find crate for typenum` / `shlex` / `num_traits` / `arrayvec`), and a mixed `TypeId` scheme,
where clap panics on the first flag it reads — `Mismatch between definition and access of
'number-nonblank' … MatchesError::Downcast` from `coreutils cat`.

`_finish-bootstrap` now cleans it too, and asserts that no `*.rlib` survived: a `cargo clean` can
exit 0 and leave everything in place (measured — it did, once, while the manifest was momentarily
invalid, leaving 6774 files behind, and the stale rlibs only showed up minutes later as that E0463
burst). Check by hand with:

```sh
find coreutils/target -name '*.rlib' \
  ! -newer rust/build/<host>/stage1/lib/rustlib/<triple>/lib/libcore-*.rlib | wc -l   # 0
```

## Linking minix binaries

The minix target specs are GNU-flavoured LLD targets, so rustc links a minix binary by
running a program named `lld`, resolved on `PATH` — *not* the `rust-lld` a sysroot
ships. A dev machine with LLVM installed hides that. A CI image has no LLVM, and there
the smoke scripts and every userland/coreutils recipe die with:

```
error: linker `lld` not found
  = note: No such file or directory (os error 2)
```

`tools/lld.py` is the single place that decides which linker to use: the stage1
sysroot's `rust-lld`, else the LLD under `rust/build/<host>/{lld,ci-llvm}/bin`, else a
system `lld`. The Justfile exports that path as `CARGO_TARGET_<TRIPLE>_LINKER` (per
target, never through RUSTFLAGS — build scripts must keep the host linker), and the
smoke scripts pass it to rustc as `-C linker=`. Run `python tools/lld.py` to see what
the current host resolves to.

The post-link tools of the x86 image path (`tools/mkboot.rs`, plus
`crates/kernel-boot/build.rs` for the fallback trampoline) have the same problem with
`lld`, `nm` and `objcopy`, and resolve them the same way through
`crates/kernel-boot/toolchain_tools.rs` — the sysroot only has `llvm-nm` (no
`rust-nm`), so those lookups try both names. Clang is a genuine PATH prerequisite:
neither the toolchain nor the CI LLVM artifacts ship one.

The sysroot only holds `rust-lld` when bootstrap built LLD: a Linux host gets that for
free (bootstrap turns `rust.lld` on for its host, `default_linux_linker_overrides`), a
Windows host does not — so on Windows the resolution falls through to the CI LLVM's
`lld.exe` or a system LLVM.

A published toolchain can be checked from Linux without a Linux dev box, since the
asset is a Linux one and WSL is enough:

```sh
wsl.exe -d <distro> -- python3 tools/verify-stage1.py   # or `just verify-stage1` in WSL
```

That fetches the release for the pinned commit, links `tools/std-hello.rs` for all
three minix targets with the sysroot's `rust-lld`, and checks each ELF's machine. It
is the cheapest way to catch a release that is missing LLD, or a `rustc` too new for
the host's glibc (the asset is built on ubuntu-24.04, so an older distro cannot run
it).

**Ordering trap: `cargo clean` can never be the last step before a build.** It deletes
`target/<triple>/release/<bin>`, and the kernel's `build.rs` then panics:

```
thread 'main' panicked at crates\kernel\build.rs:74:23:
kernel build.rs: boot binary ...\target\riscv64gc-unknown-minix\release\hello missing
```

So after any clean, rebuild the smoke-test binaries before any `just build-*`:

```sh
cargo clean
python tools/build-std-hello.py all   # /bin/hello for all three triples
python tools/build-c-hello.py         # helloc + ctest (x86)
```

**An orphaned QEMU blocks the clean.** A leftover `qemu-system-*` holds
`target/images/<triple>/disk.img` and `cargo clean` dies with
`failed to remove file ...\disk.img: ... being used by another process. (os error 32)`.
Check `ps -W | grep -i qemu` before cleaning, and kill leftovers **by PID** (never by image
name — that would take out any VM the operator has open).

This fork also denies warnings (`error: warnings are denied by build.warnings
configuration`), so a cosmetic slip while resolving conflicts fails the build. One that
actually happened: wrapping the minix arm of `sys/exit.rs` in `unsafe { }` — the call is
`crate::sys::syscall::exit`, a *safe* re-export of `minix_rt::exit`.

## Never run the recipe's submodule step by hand

`just bootstrap` starts with `git submodule update --init rust coreutils`. While the parent
still pins the *old* submodule commit, that detaches `rust/` onto it and undoes the rebase
checkout. Skip it (submodules are already initialized) or let the operator update the
parent's pointer first.

## Revalidate

Smoke tests use the stage1 rustc directly — no cargo, no network:

```sh
python tools/build-std-hello.py all      # /bin/hello for all three minix triples
python tools/build-c-hello.py            # helloc + ctest (x86 only)
```

The C smoke test compiles with the host's clang, so its version has to stay at least as
new as the dev machines': syntax a newer clang accepts silently is a hard error on an
older one. A C2y `0o` octal literal in `tools/c-include/fcntl.h` compiled on a dev
machine and failed CI's clang 18 with `invalid suffix 'o00'`. `toolchain-release.yml`
therefore installs clang 22 from apt.llvm.org, and `LLVM_VERSION` there is the pin to
bump when the dev machines move - nothing in the tree guards the other direction, so a
local clang newer than the image's can still accept syntax CI rejects.

Sanity-check each `target/<triple>/release/hello`: ELF machine `0x3e` x86-64, `0xf3`
RISC-V, `0xb7` AArch64.

Then rebuild the images and boot (boot sequence details are in the `minix-boot-process`
skill):

```sh
just build-x86   # userland + coreutils (kernel build.rs requires /bin/coreutils on x86_64),
                 # then kernel, trampoline and the embedded images
just mkfs-x86    # writes target/images/x86_64-pc-minix/disk.img
```

For the other arches use `just build-<arch>-boot` + `just mkfs-<arch>` (`arch` = `riscv64`,
`aarch64`) and take the QEMU arguments from the matching `run-<arch>` / `test-boot-<arch>`
recipe rather than copying them from here: RISC-V/AArch64 add
`-global virtio-mmio.force-legacy=off` and use `-device virtio-blk-device` instead of
`virtio-blk-pci`.

QEMU's `-nographic` puts the guest serial console on stdio, so commands can be piped in and
the transcript captured. Boot reaches the shell within ~10 s, so send the command a few
times to cover the window, and bound the run:

```sh
( sleep 10; printf 'hello\n'; sleep 10; printf '/bin/hello\n'; sleep 10; printf 'hello\n'; sleep 12 ) \
  | timeout 140 qemu-system-x86_64 -nographic -m 256M -no-reboot -vga none \
      -device bochs-display,id=fb0 -kernel target/trampoline.elf \
      -device loader,file=target/kernel.bin,addr=0x200000 \
      -drive if=none,id=disk0,file=target/images/x86_64-pc-minix/disk.img,format=raw,cache=writethrough \
      -device virtio-blk-pci,disable-legacy=on,drive=disk0 \
      -netdev user,id=net0 -device virtio-net-pci,disable-legacy=on,netdev=net0 \
      -device virtio-tablet-pci,display=fb0 > target/boot_hello.log 2>&1
```

A good run shows a clean cold boot (`/sbin/ds`, `rs`, `pm`, `sched`, `vfs`, `vm` loading as
ELF64 at `0x1000000`, then `init: pid=N` and a `#` prompt) and, for each `hello`, an
incrementing pid plus:

```
hello from minix std
pid=12
alloc: churn + realloc + align ok
  thread 0: shared=1 tls=1
  ...
threadstd: all joined, shared=4 (expected 4)
```

That transcript exercises exactly what a rebase breaks: std `_start`, `println!` through
VFS/serial, `process::id()` via PM, the mmap free-list allocator (4096 alignment),
per-thread TLS, `join`, and the futex-backed stdout lock. Grep the log for
`panic|fail|error` and expect no matches.

`just test-boot-x86` and `just test-qemu-x86` are the self-terminating suites (they exit QEMU
through isa-debug-exit) when pass/fail codes are more useful than a transcript.

**Bound QEMU runs with SIGKILL.** MSYS `timeout`'s SIGTERM does not terminate a native Windows
QEMU, so `timeout 240 qemu-system-riscv64 …` leaves an orphan that later blocks `cargo clean`
(os error 32 above). Use `timeout -s 9 240 qemu-system-…` and verify with
`ps -W | grep -i qemu` afterwards. Only the x86 suite self-exits; RISC-V/AArch64 have no
exit-code device, so their pass/fail must be read from the serial log (`ALL TESTS PASSED` vs
`FAILURES: n`).

## Fast API-drift audit

Instead of rebuilding after each error, enumerate in one pass what upstream now expects of
the fork's dispatchers:

```sh
git --no-pager grep -n -A 5 'target_os = "minix"' HEAD -- library/std/src/sys
git --no-pager diff <pre-rebase-tag> HEAD -- library/std/src/sys/io/mod.rs <other dispatchers>
```

Diff each dispatcher against the pre-rebase tree and grep that diff for `minix`: any arm
upstream edited is a candidate break (this is how the `error_string` →
`format_error(errno, f: &mut fmt::Formatter<'_>) -> fmt::Result` change in `sys/io/error`
was caught). Glob re-exports (`pub use ...::*`) hide breaks until later; explicit name
lists fail loudly.

Shapes worth knowing as of the current upstream:

- Futex moved to `library/std/src/sys/sync/futex/<os>.rs` with a `cfg_select` in `mod.rs`.
  The old `pal/<os>/futex.rs` globbed into `crate::sys` is gone, so the minix file must move
  too and the dispatcher needs a `target_os = "minix"` arm. It must supply `Futex`,
  `Primitive`, `SmallFutex`, `SmallPrimitive`, `futex_wait`, `futex_wake`, `futex_wake_all`.
- Five consumers import those from `crate::sys::sync::futex`: `sync/{condvar,mutex,once,rwlock,thread_parking}/futex.rs`.
- `rustc_target` spec API is reachable from `spec/base/<os>.rs` the same way upstream's own
  base modules use it (`TargetOptions` fields, `Target`/`TargetMetadata`, and
  `TargetOptions::link_args`; `singlethread` is deliberately a private field but visible
  from base modules, which set it too).

## Checklist

- [ ] `range-diff` shows every commit `=` (or `!` entries reviewed line by line) and no conflict markers remain
- [ ] `ps -W | grep -i qemu` is empty before any `cargo clean`, and the smoke binaries were rebuilt after the last clean
- [ ] `coreutils/target` holds no rlib older than the sysroot's `libcore` (`_finish-bootstrap` asserts this)
- [ ] fork-only files byte-identical: `git diff --stat <pre-rebase-tag> HEAD -- 'library/std/src/sys/pal/minix/**' 'library/std/src/sys/pipe/minix.rs' 'library/std/src/sys/net/connection/minix.rs' 'library/std/src/sys/thread/minix.rs' 'compiler/rustc_target/src/spec/targets/*minix*'`
- [ ] no conflict markers; `library/std/Cargo.toml` and `library/Cargo.lock` still carry the minix deps
- [ ] `x.py build library/std library/proc_macro` green (warnings are errors)
- [ ] `python tools/lld.py` prints a linker (the smoke scripts pass it to rustc)
- [ ] smoke-test ELFs carry the right ELF machine
- [ ] boot transcript clean, `/bin/hello` threads + TLS + allocator all pass
- [ ] the operator folds the adaptation edits into the fork commits and updates the parent's submodule pointer
- [ ] the stage1 for that *new* pin is published first (`toolchain release`), because CI's arch tests
      consume `stage1-<pin>` and stop at `just fetch-stage1` until the release exists
